为什么是 Rivet

Racket 擅长逻辑， 商业应用需要原生 UI。

过去，Racket 后端到现代一等桌面技术栈之间没有直通路——而商业应用恰恰越来越多地建立在这些技术栈上。Rivet 补上这条路。

一等原生 UI

Windows 用 WinUI 3，macOS 用 SwiftUI/AppKit，Linux 用 GTK4。每个应用都保留对应平台的第一方 UI 与行为。

一个后端契约

类型化 RPC、事件、共享状态、取消与生命周期——全部走同一套 RVT1 协议，所有原生宿主共用；同一份 schema 还可投影到 Keel——与 Glaze 共享的传输无关契约。

生成的原生客户端

raco rivet build 读取 RPC、Event、State、Record 与 Enum schema，生成类型化 Swift/C++/Kotlin API；带版本的 JSON 基线可在 CI 中拦截破坏性变更。

嵌入式 Racket CS

Racket 运行时住在应用进程内的专属线程上——没有需要额外管理的外部后端进程。

精确运行时匹配

Rivet 要求 Racket 9.0+（CS 运行时），按原样部署所安装的 Racket CS 运行时，绝不悄悄回退到相近版本。

线程安全是设计出来的

原生 UI 代码从不直接操作 Racket/Chez 值——原生侧看到的只有分帧的 RVT1 消息与生成值。

实时图表

三端桌面宿主的滚动时序原生图表控件，走同一条类型化数据面：rivet/chart 环形缓冲与缺口检测的二进制批。

内置更新器

签名发布 feed 带安装包、SBOM 与第三方声明；共享更新器覆盖 macOS bundle 换装、Windows MSI 交接与 Linux AppImage 替换——产品只提供策略与 UI，无需重造安全关键管线。

可链接的发布包

宿主以发布包方式接入 Rivet——macOS 走可按 tag 解析的 SwiftPM 包，Windows 与 Linux 走静态库——绝不把 Rivet 源码编进自己的构建。

生态定位

两个项目， 两种取舍。

Racket 桌面技术栈：Rivet 做一等原生应用，Glaze 做 Web 技术桌面应用。它们各守一种取舍，互不替代。

Rivet Glaze
UI 技术栈 WinUI 3 / SwiftUI / GTK4 HTML/CSS/JS + WebView
原生控件 first-party OS UI no
单一 UI 代码库 no yes
最适场景 platform-native commercial apps web-tech desktop apps
选型判断

先完成一个可验证的结果。

当第一方原生交互值得维护 SwiftUI、WinUI 3、GTK4 三份界面时，选择 Rivet。共享领域逻辑归 Racket，渲染与系统交互归原生宿主。需要共享 HTML/CSS 界面时可评估 Glaze。

需要 Racket CS 9.0+ 和目标平台原生工具链。桌面交付有明确能力与验收分级；移动运行时或伴随端基础不等于已生成、签名和打包的应用工作流。

在生成项目内运行 inspect 和 doctor，完成一个后端修改，并在打包原生应用中观察持久化结果。跨宿主保持一个产品交互契约，快捷键、焦点和窗口行为遵循各系统习惯。单元测试或截图本身不能证明产品一致性。
